# Database — предварительная схема

## WordPress / MariaDB
Стандартные таблицы WordPress; собственные данные добавлять через плагин и согласованные механизмы WordPress.

## PostgreSQL — News Engine
Предварительные сущности:
- sources
- raw_items
- articles
- article_sources
- processing_jobs
- fact_checks
- duplicate_groups
- ai_generations
- published_posts
- audit_logs

## PostgreSQL — Football Data
Предварительные сущности:
- competitions
- seasons
- teams
- players
- fixtures
- match_events
- match_statistics
- lineups
- standings
- api_sync_logs

## Правила
- Схему уточнить после проверки конкретного API.
- Сохранять внешний provider ID.
- Использовать уникальные ограничения для идемпотентности.
- Хранить время обновления и источник данных.
- Не дублировать без необходимости данные, уже надёжно хранящиеся в WordPress.

## Владение данными и ключи
- Для статьи News Engine создать устойчивый article_uuid с уникальным ограничением; повторная доставка той же статьи должна находить ту же запись WordPress.
- В published_posts хранить связь article_uuid с WordPress post ID, состояние доставки и время последней попытки.
- На стороне football-media-core обеспечить уникальную связь ключа интеграции с WordPress-записью, чтобы повторный запрос не создавал дубль.
- Для футбольных записей сохранять провайдера, тип сущности, внешний ID и время обновления; для сущностей без глобально уникального ID использовать составной ключ.
- В WordPress хранить только проекцию полей, нужных публичным страницам. Синхронизация не должна перезаписывать редакционные поля.
- Redis/Celery отвечает за очередь заданий и не является источником истины для материалов или футбольных данных.
