# API Integrations

## Football data
Первый кандидат — API-Football. До выбора платного тарифа проверить:
- нужные турниры и сезоны;
- расписание и результаты;
- live fixtures и частоту обновления;
- события матча;
- составы;
- статистику;
- таблицы;
- лимиты и коммерческие условия.

## WordPress REST API
Использовать отдельную сервисную учётную запись и Application Password. Секреты хранить только на сервере.

## Надёжность
- Тайм-ауты.
- Ограниченные повторные попытки с backoff.
- Обработка rate limit.
- Кэширование.
- Идемпотентность.
- Логи запросов без секретов.

## Важно
Не считать поле доступным, пока оно не проверено для выбранных турнира и сезона на нескольких подходящих матчах. Покрытие в документации провайдера — предварительный фильтр, а не гарантия наличия поля в каждом ответе. Это ограничение описано в [официальной документации API-Football](https://api-sports.io/documentation/football/v3).

## WordPress REST API: доступ
- Использовать отдельную сервисную учётную запись и Application Password только через HTTPS; не использовать администратора.
- Выдать учётной записи только необходимые права. Если автопубликация выключена, не выдавать право публикации.
- Использовать отдельные Application Password для окружений; хранить их на сервере, не передавать в браузер и отзывать при утечке или смене интеграции.
- Маршруты плагина должны проверять права пользователя, валидировать и очищать входные поля. См. [руководство WordPress по аутентификации](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/) и [созданию REST-маршрутов](https://developer.wordpress.org/rest-api/extending-the-rest-api/adding-custom-endpoints/).

## WordPress REST API: идемпотентность и аудит
- Для статьи использовать устойчивый article_uuid из News Engine как ключ интеграции.
- Плагин должен предоставлять операцию upsert по этому ключу и хранить уникальное соответствие ключа WordPress post ID. Повтор того же запроса возвращает ту же запись; конкурентные повторы не создают дубли.
- Обновление уже существующей статьи должно учитывать версию и ручные правки редактора; автоматическая синхронизация не перезаписывает редакционный текст без явного правила.
- При сетевом тайм-ауте сначала проверить запись по ключу интеграции, затем повторять запрос. Ограниченные повторы с экспоненциальной задержкой и jitter применять для сетевых ошибок, 408, 429 и временных 5xx; учитывать Retry-After. Ошибки постоянного класса не повторять автоматически.
- Логи фиксируют request/correlation ID, article_uuid, номер попытки, HTTP-статус, WordPress post ID, время и исход операции. Не сохранять пароли, токены, заголовок Authorization или полный секретный запрос.
- audit_logs фиксирует решение о публикации, версию правил, результат проверок, источник решения, автора или процесс, временные метки, результат REST-доставки и исправления.
